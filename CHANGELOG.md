## 0.0.1

- Establish the first stable Agent Marketplace baseline for all supported hosts.

## 0.0.2

- The repository-portable vault gate that setup installs at `.github/agentrof/vault-gate.pyz` now gives the package's own verdict on two kinds of project where it failed. Its `check` failed `backlog:approved`, or `backlog:draft`, on every project with a backlog with `process switch registry cannot be read`, while the package's own `backlog_compile.py check` passed on the same project: the archive held the backlog compiler and the Process Policy module it imports, but not the process switch registry that module reads. The task input policy, the story size measures, the Delivery document contract, verification policy and owner decision classes, the code review panel data and the CI workflow template were missing the same way. The installer now closes the archive over each path under `skill-content/` or `templates/` that a bundled script names, as one string literal or as literals joined with `/`, and copies a named file as well as a named directory; a named path the package does not hold is skipped. The gate also failed `solution-design` when an accepted Solution decision named an installed method skill such as `python-fastapi`, because `landscape_check.py` resolves the installed skills from the folders under `skill-content/` and the archive held only the folders whose data it bundles. The archive now lists every folder under `skill-content/` and `templates/`. It stays byte-for-byte reproducible, and setup replaces an installed gate whose bytes differ, so running setup after the update installs the fixed gate.
- A private verification clone that differs from its commit now names the paths. Git can leave a tracked file out of a checkout that still exits 0, and the clone then differs from its commit before any command ran, yet `environment --verb up` refused with only "runtime checkout changed; only teardown is allowed before a new verification session" and a command run recorded only `candidate_intact` false, which read as a file the command had changed. The runtime refusal now reads "runtime checkout changed (missing <path>); ...", a QA command run, a pre-handoff regression run or a runtime event that is not intact records the paths as `checkout_difference`, and a freeze that such a pre-handoff run refuses names them as well. A path the checkout lacks is marked missing, any other is marked changed, and at most five are named before a count of the rest. What each refusal allows is unchanged.

## 0.0.3

- Codex now loads the same user context as Claude Code. The generated `CLAUDE.md` imports `CLAUDE.user.md` and `workspace/memory/agent-marketplace.md`, `me.md` and `profile.md`, but the generated `AGENTS.override.md` named only `AGENTS.user.md`, and Codex has no import syntax, so a Codex session never read the memory files, and the working preferences and profile they hold applied on Claude Code only. Both files now take their list from one shared declaration: Claude Code keeps its `@` imports, and `AGENTS.override.md` gains a `Load user context` section that tells Codex to read and follow `AGENTS.user.md` and the same memory files, in the same order, before any work, skipping a file that does not exist. The generated `CLAUDE.md` is unchanged. Running setup after the update rewrites `AGENTS.override.md`.
- The Claude Code host projection's `inspect` now shows what `apply` will do. Setup step 4 runs `generate_claude_project.py inspect` to find and resolve every preserve or discard choice for a user-owned instruction companion, yet `inspect` reported only the surfaces the project already held: `changes` and `choice_requests` were always empty and `target_surfaces` equaled `current_surfaces`, so a hand-written `CLAUDE.md` showed no open choice and none of the instruction roots or role agents that `apply` then wrote were listed. `inspect` now builds the plan `check` builds, with the same `--choice`, `--seed-user-files` and `--scope`, and reports it the same way: the planned changes, the open choice requests and the target surfaces, and it stops where `check` stops, such as on a root another team owns. It still reads no model list and writes nothing, and `apply` still refuses to write while a choice is open. The Codex projection's `inspect` already built this plan.
- A stable release is now a tag of an approved `main` commit, with no release branch, release pull request or second test run. The last commit of an ordinary pull request is the release commit: `python3 tools/release.py bump` consumes the pending changesets, sets every version surface, appends the `CHANGELOG.md` section, writes `.release/stable.json` and regenerates `dist/`, and `check-pr` accepts release-owned changes only when that commit equals `bump` replayed on its parent, so the pull request's CI tests the final release tree once. After the merge, `python3 tools/release.py ship --version X.Y.Z` dispatches the new `Release` workflow: it verifies the commit's release state, waits for `main`'s own validation of that exact commit instead of testing it again, moves `stable` and pushes the annotated tag in one atomic exact-lease push, installs both hosts from the public `stable` channel and publishes the immutable Release with the `CHANGELOG.md` section as its notes, in about three minutes. `Prepare stable release`, `Publish stable release`, the release pull request and merge queue gates, the release test profile and the reuse of host install evidence are removed, and every pull request installs both hosts fresh.
- On native Windows, setup now asks before it turns on Git long paths for the project. Item and Integration worktrees share the project repository's local Git config, and Git for Windows leaves out of them, while its checkout still exits 0, every tracked file whose path reaches 260 characters or whose directory reaches 248 unless `core.longpaths` is set. While that local config does not turn `core.longpaths` on, `setup_project.py inspect` returns the `git.core_longpaths` choice request, and `apply` refuses until `--choice git.core_longpaths=set` or `--choice git.core_longpaths=leave` answers it, so a script that runs setup on Windows passes one of them. `set`, the recommended option, runs `git config --local core.longpaths true`; `leave` writes nothing, and apply warns, without failing, with every tracked file Git for Windows would leave out of the deepest Item or Integration worktree the Delivery code would create for the next Delivery and the backlog's Stories, each with its reason: its directory reaches 248 characters, or else its own path reaches 260. macOS and Linux never ask, and neither does a value Git already reads as true.
